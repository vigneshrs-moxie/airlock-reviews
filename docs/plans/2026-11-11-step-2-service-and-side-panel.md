# Airlock Step 2: Service and Side Panel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local service that runs reviews and remembers them, and a Chrome side panel beside any GitHub pull request that starts a review, shows the brief, the change map and the findings as they arrive, jumps the page to a finding's line, copies a fix prompt, and records dismissals.

**Architecture:** Two new packages. `@airlock/service` is a small HTTP server on `127.0.0.1` around the engine's `runReview`: it starts reviews, streams their events, serves stored reviews and records dismissals. `@airlock/extension` is a Manifest V3 extension built with WXT: a side panel page that talks only to the service, a content script that drives GitHub's Files changed page, and a minimal background worker. The contract between them is a set of zod schemas in `@airlock/shared`, so the two sides are built in parallel against it.

**Tech Stack:** Node 24 ESM, TypeScript, zod 4, `node:http` (no web framework), Vitest; WXT with React 19 for the panel, happy-dom and Testing Library for component tests, Playwright (Chromium) for the loaded-extension tests.

**Spec:** `docs/design/2026-11-10-airlock-design.md` (sections 3, 7, 8, 10, 11). Visual reference: the approved prototype, whose screens are written by `docs/design/prototype/gen.py` (copied into the repository in Task 1; the prototype's build brief is beside it). Picks made on the prototype: a review starts on a click; posting comes in step 3; private notes in the diff come in step 4.

## Global Constraints

- Everything in step 1's constraints still holds (Node `>=24`, `strict`, no `any` in exported signatures, `execFile` with argument arrays, tests never touch the network, GitHub or Claude, `AIRLOCK_HOME` is a temporary folder in tests, severity words, one commit per task ending with the `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>` line, `npm run check` passing).
- **Nothing in step 2 writes to GitHub.** No route posts, comments, approves or merges. The only `gh` calls are reads.
- The service listens on `127.0.0.1` only, port `4611` (`AIRLOCK_PORT` overrides). It never binds another address.
- Every route except `GET /hello` requires all three: a `Host` header of `127.0.0.1:<port>` or `localhost:<port>`; `Authorization: Bearer <token>` (compared in constant time); and, when an `Origin` header is present, that it equals the paired extension origin. The service never sends an `Access-Control-Allow-*` header and answers `OPTIONS` with 403.
- The extension holds no GitHub token and no model key. It talks only to the service and to the GitHub page it sits beside.
- Every string that came from a review, a pull request or the service is rendered as text. No `innerHTML`, no `dangerouslySetInnerHTML`, no Markdown rendering, no link whose address comes from review text. Links are built by code from a repository name, a number, a path and a line.
- The content script never makes a network request and never reads or writes the pairing token.
- Text written to a pack's `learned` files is exactly the text the person saw and confirmed in the dismiss sheet: one line, at most 500 characters, no control characters. Nothing generated by a model is written there without that step, because learned entries are given to later reviews as instructions.
- Selectors for GitHub's pages live in one module of the extension, each with a name, and a selector that finds nothing is reported (to the panel and the console), never ignored.
- Words on screen follow the prototype. Verdict labels, severity words and stage names are shown as words, never as raw ids.

## Review Focus

1. **A web page tries to use the service.** Any site open in the browser can send requests to `127.0.0.1:4611`. Expected: without the token it gets 401; with a foreign `Origin` it gets 403 even with the token; a preflight gets 403; a request with a rebinding `Host` gets 403; no response can be read cross-origin. Owned by Task 3.
2. **The panel is closed or the tab is reloaded while a review runs.** Expected: the review keeps running; reopening the panel on that pull request attaches to the same run and shows every event from the start, without starting a second review. Owned by Tasks 4 and 8.
3. **The service stops or was never started.** Expected: the panel says so in plain words with the command to start it, keeps the last review it had on screen readable, and recovers by itself when the service is back. Owned by Tasks 8 and 9.
4. **Review text that looks like markup or a link.** A finding title such as `<img src=x onerror=…>` or `[click](javascript:…)`. Expected: shown as those characters. Owned by Tasks 9 to 11, checked again in Task 13.
5. **The line is not on the page.** GitHub loads files lazily and can virtualise large diffs; a finding can be outside the changed lines; the tab can be on the Conversation page. Expected: the panel always does something visible and says what it did (jumped to the line, showed the file, opened the Files changed page, or opened the file in a new tab), and never fails silently. Owned by Task 12.

Rules for the router: bodies are JSON only (`Content-Type: application/json`), at most 64 KB, parsed then validated by the route's schema; an unknown route is 404, a wrong method 405, a bad body 400 with the first problem in words; an exception in a handler is 500 with `{ error: 'Airlock had a problem: <message>' }` and the stack goes to the log only; every response has `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. `GET /hello` is the only open route and returns only `Hello`. `POST /pair` requires the token and an `Origin` header; it records the origin when none is recorded (`paired`), accepts the same one again (`already`), replying with `PairReply` in both cases, and refuses a different one with 409 and the words `Airlock is already paired with another copy of the extension. Run "airlock-service unpair" and pair again.`

### Task 4: Reviews through the service

**Files:**
- Create: `packages/service/src/runs.ts`, `sse.ts`, `routes.ts` (review routes), `test/runs.test.ts`, `test/reviews.test.ts`

**Interfaces:**
- Consumes: `runReview`, `ReviewRequest`, `EngineDeps`, `latestReview`, `fetchPr`, `loadPack`, `selectPacks`, `parsePrRef` from `@airlock/engine`; Task 2's schemas; Task 3's router.
- Produces:

```ts
// ServiceDeps is Task 3's
class Runs {            // in memory
  start(body: StartReviewBody): { runId: string; reused: boolean }       // throws LimitError when two other runs are active
  running(repo: string, number: number): string | null
  events(runId: string): { past: ServiceEvent[]; subscribe(fn: (e: ServiceEvent) => void): () => void; finished: boolean } | null
}
```

Routes: `GET /status` → `ServiceStatus`; `GET /pr?repo&number` → `PrSummary`; `POST /reviews` → `StartReviewReply` (429 `Two reviews are already running. Wait for one to finish.` at the limit); `GET /reviews/running?repo&number` → `{ runId }` or 404; `GET /reviews/:runId/events` → `text/event-stream`; `GET /reviews/latest?repo&number` → `LatestReply` or 404.

Rules: one run per pull request (a second `POST` for the same repository and number while one runs returns the same `runId` with `reused: true`); at most two runs at once; every event of a run is kept in order so a later listener gets all of them from the start, then live ones; a run that rejects ends with `{ type: 'failed', message }`; a finished run's events are kept for ten minutes, then dropped (after that the panel uses `GET /reviews/latest`). The stream writes `data: <one-line JSON>\n\n` per event and `: keep-alive\n\n` every 15 seconds, and ends after `done` or `failed`; a listener that disconnects is removed and the run goes on. Engine dependencies: `{ exec: realExec, runner: withRetry(createSdkRunner(), 1), now }`.

The team kit's pack is never written to.

```ts
  | { kind: 'review'; pr: PrSummary; latest: LatestReply; stale: boolean }      // stale: the pull request's head moved since
  | { kind: 'problem'; pr: PrSummary | null; message: string }
type UserAction = { type: 'pair'; token: string } | { type: 'start'; depth: Depth; packIds?: string[] } | { type: 'show-earlier' }
  | { type: 'dismiss'; body: DismissBody } | { type: 'restore'; fingerprint: string } | { type: 'retry' }
function reduce(state: PanelState, action: Action): PanelState                 // pure; Action = UserAction results and service events
function startPanel(deps: { client: ServiceClient; tab: TabWatcher; onState: (s: PanelState) => void }): { dispatch(a: UserAction): void; stop(): void }
```

Rules: every response from the service is parsed with the shared schemas; a body that does not parse is a `problem`, never rendered. The token lives in `chrome.storage.local` and is read only by the panel page. On load and whenever the tab's address changes to another pull request: `hello` (offline → `offline`, retried every 5 seconds while the panel is open; not paired or 401 → `unpaired`), then `pr`, then `running` (attach to its events) or `latest` (→ `review`) or neither (→ `ready`). A lost stream while a review runs is re-attached up to five times, replaying from the start and replacing the stage list. Stage names are turned into the prototype's words in one table (`intake` → "Reading the pull request", and so on for every stage name the engine emits, with the raw name as the fallback).

### Task 12: Driving the GitHub page

**Files:** `packages/extension/src/page/{selectors,locate,jump,soft-nav}.ts`, `entrypoints/github.content.ts`, `src/state/jump.ts` (panel side), unit tests on the two fixture pages, `e2e/jump.spec.ts`

**Interfaces — Produces:**

```ts
// messages (panel -> content script of the panel's own tab, via chrome.tabs.sendMessage)
type JumpRequest = { type: 'airlock:jump'; anchorId: string; path: string; line: number | null }
type JumpReply = { ok: true; how: 'line' | 'file' | 'asked' } | { ok: false; reason: 'not-files-page' | 'file-not-on-page' }   // plus `view: 'react' | 'classic' | null` and `missing: string[]` (selector names that found nothing) on every reply
// page
function detectView(doc: Document): 'react' | 'classic' | null
function findFile(doc: Document, anchorId: string): HTMLElement | null
function findLine(doc: Document, view: 'react' | 'classic', file: HTMLElement, anchorId: string, line: number): HTMLElement | null
function mark(rows: HTMLElement[]): void                      // one class, removed from the previous target
// panel
function jumpTo(tabId: number, pr: { repo: string; number: number; headSha: string }, place: { path: string; line: number | null; inDiff: boolean }): Promise<string>   // the sentence to show
```

Behaviour of `jumpTo`, in order: (1) a place whose path is not among the review document's `files` opens `blobUrl(repo, headSha, path, line)` in a new tab: "Opened <path> in a new tab; it is not part of this pull request." (2) When the tab is not on the Files changed page, or no content script answers: navigate the tab to `filesUrl(repo, number, anchorId, line)` and wait for it to finish loading. (3) Send the request. The content script first sets the page's address fragment to `#<anchorId>R<line>` (or `#<anchorId>` when there is no line): this is GitHub's own permalink form and makes GitHub scroll and mark the line in both views. It then looks for the row for up to three seconds to add Airlock's mark. Row found: "Showing <path>:<line>." File found but not the row, for a line outside the changed lines: "Showing <path>; that line is outside the changed lines." File found, row expected but not found: "Asked GitHub to show <path>:<line>." File container not on the page: "GitHub has not loaded <path> on this page yet. Scroll to it, then try again." (4) Neither view recognised: the fragment is still set, and the sentence is "Asked GitHub to show <path>:<line>. Airlock does not recognise this version of the page." with the names of the selectors that found nothing, which the Packs screen also lists. The content script handles only this one message type, checks that the sender is this extension, and never navigates anywhere except by setting the hash on the same page. It re-reads the view after GitHub's soft navigations (Task 1's notes name the events).
