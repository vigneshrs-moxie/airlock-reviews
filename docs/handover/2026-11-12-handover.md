# Airlock hand-over

Written 2026-11-12, at the end of the four-step build. This is the one page to read before first use: what is built, how to turn it on, what was never run, what only you can check, and the decisions that were made for you while you were away.

## What is built

All four steps are on `main`.

1. **The engine and the replay.** Reviews a pull request in connected groups of files, challenges each finding, and gives at most five ranked findings with a verdict. The replay measures it against the senior reviewer's past reviews.
2. **The service and the side panel.** A local service on 127.0.0.1:4611 and a Chrome side panel that opens beside a GitHub pull request.
3. **Posting, reviewing again after a push, and learned lines.** Comments are posted only on your click, always as a comment (never an approval, a change request, a merge or a resolve). After a push, only what changed is reviewed and earlier findings are marked fixed, moved or still open. What you dismiss is learned and listed under Packs.
4. **Notes in the diff and the Extensions pack.** Private notes under the lines of GitHub's Files changed view, and a pack that reviews the five extension repositories against the tech team's extension kit, which is downloaded at review time.

Tests on the final tree: 2,493 passed and 4 skipped, with the comparisons against the two kits switched on (they need a copy of each kit on disk; without one, three more tests are skipped). End-to-end flow in a real browser against a stand-in service: 40 of 40 steps. The built service was also started once on a spare port with an empty home folder, answered, and was stopped.

## Turn it on

The guide is `docs/guide/install.md`. In short, from this folder:

1. `npm run service` and leave that terminal open (or `npm run service:install` once, to start it at login).
2. In Chrome: `chrome://extensions`, Developer mode on, **Load unpacked**, choose `packages/extension/.output/chrome-mv3` (press Cmd+Shift+. in the folder chooser to see `.output`). The folder is already built from `main`.
3. Open a pull request, press the Airlock button, and paste the last line of `npm run service -- token` into the panel.

Reviews run on your Claude login. On the replay, a Standard review on Opus cost $1.70 to $7.10 at list price and took 1 to 7.5 minutes.

## What was never run

- **No comment has ever been posted to GitHub.** Every post in the build went to a stand-in. The first real post is your click.
- **A review of a merge commit has never been run with a real model.** It is tested with real git and a stand-in model only.
- **The full replay was not run.** The small set was: 6 of the 9 known problems were in the top five (67%), for $22.33 in about 13 minutes. The three largest pull requests, #143 and the clean pull requests were not run again after the last fixes. `docs/replay/2026-11-step-1-report.md` has the detail and the commands.
- **GitHub's signed-in Files changed page was never seen.** The Chrome profile Claude drives is not signed in to GitHub, so the selectors for GitHub's newer view are unconfirmed.
- **The real service, the login item and the extension in your Chrome.** The build never started the service on port 4611, never installed the login item and never loaded the extension into your Chrome.

Real runs that were made, all read-only on GitHub: a review again of moxie-portal #146 ($1.18) and #129 (3 fixed, 3 moved, 1 still open, 4 new; $5.14), and a first review of moxie-click-to-dial #1 with the Extensions pack (approve after fixes, 7 findings, $3.90, 5 min 25 s).

## What only you can check

1. **Logins under the service.** That `claude` and `gh` are signed in for the service, and still are when it starts at login.
2. **Jump to line and notes on a real page.** On a pull request's Files changed view: a finding's jump lands on its line, and notes sit under the right lines. Scroll a long file away and back (does a note end up under another line?). Add a comment and a reply on a line that has a note. Look for errors in the page's console.
3. **Open in Airlock.** Pressing it on a note opens the panel on that finding. It works in the test browser; whether your Chrome counts the press as your own gesture is unconfirmed.
4. **The first real post.** It appears once, on its line, as a comment. Nobody is notified by text Airlock drafted. Posting a comment on your own pull request works. The record's `bodyHash` matches the review text GitHub shows.
5. **After a push.** Press review again without reloading the GitHub tab: the line under the verdict should say the page was opened before the commit this review is of, with a Reload button, and after the reload the notes should sit on the right lines.
6. **The replay's Fix findings on clean pull requests.** `replay-work/opus-standard/report.md` lists them; each needs you to say right or wrong.
7. **Two characters in the extension kit.** Two entries in the kit's `calibration.md` start with a stray `'`, so they are read as belonging to no entry.

## Decisions most worth a look

Each was made without asking, to keep the build moving. Say the word and it is changed.

| Decision | What it costs if it is wrong |
|---|---|
| Reusing the review of PR #1 when PR #2 opens for the same code is not built. PR #2 gets a full review of its own. | A second full review's cost and minutes at PR #2. |
| Posted comments carry no "made with Airlock" line. | One line to add if you want it. |
| Text Airlock drafts never notifies anyone: a name is written `@ name`, and `#12` is escaped. Any `@name` you type yourself is listed before you post, an email address included. | A drafted comment reads slightly oddly where it names a person; a notice appears for a typed email address. |
| If GitHub answers a post with a server error or not at all, Airlock says it does not know whether it was posted, and will not post again until you press "It was not posted" (which first checks GitHub's own list). | After a GitHub outage you look at the pull request once. |
| An open pull request is compared with its base branch as it is now, not the base GitHub recorded. | A pull request whose base moved a lot shows a slightly different diff from GitHub's page. |
| A finding is dropped by the challenge only on proof: the exact code elsewhere, or a whole dated entry that says the behaviour is meant. | More findings stay listed that you would have waved through; you dismiss them and Airlock learns. |
| After a push, vanished questions and notes are marked fixed without a second check ("not checked further"). Blocks and Fixes are checked. | A question whose code moved elsewhere could be marked fixed. |
| A pull request's code is checked out without your git settings, filters and hooks. | Files kept in git-lfs are reviewed as their pointer text. |
| The pairing token is kept in Chrome's local storage for the extension, so you pair once. | Anything that can read that Chrome profile's extension storage can read the token; the service also checks where a request comes from. |
| A review is stopped as failed after 90 minutes. | A pull request larger than anything seen so far would be cut off. |
| Airlock never reloads your GitHub tab by itself; it offers a Reload button. | One extra click, after an extension reload or a push. |
| A learned line saved from a repository with no pack of its own applies to that repository only. | A lesson from one project is not carried to another unless you write it by hand. |
| The Extensions pack attaches six of the kit's files, `lenses.md` among them; `lens-rules.md` and `asks.md` are left out. If the kit cannot be downloaded and no copy is cached, the review stops and says so. | About 180 more lines in each request of an extension review. An extension review cannot start while GitHub is unreachable and no copy of the kit is cached. |
| In an extension repository every file the manifest or a loaded script loads is read closely whatever its folder, a changed bundled or minified script is at least skimmed, and when what the extension loads cannot be fully followed no file is trusted as a test. | More to read, so a higher cost, on a pull request that changes a bundled library or is very large. |
| A note is drawn only when the commit the review is of is the commit the page showed when it last loaded. | One click on Reload after reviewing again; see the limit below for a page that was already open. |

## Known limits

- **A page that was already open.** When the panel is opened beside a GitHub page that was loaded before a push, and a review of the newer commit is already stored, its notes can be drawn on the older diff. Reloading the tab puts it right. Closing this fully needs the page to report the commit it shows, which needs the signed-in page to be seen first.
- **A note and GitHub's own comment rows.** A note sits directly under its line, above GitHub's comment box for that line. Whether that upsets commenting on that line is on the list above.
- **A note the page keeps removing** is put back at most five times in ten seconds, then left out until the page changes again; the panel still counts it as shown meanwhile.
- **The extension checks** do not follow a script list held in a variable, a worker made from a built address, or pages whose HTML uses entities in a script address; such a file is still skimmed if it is bundled or minified, and read normally otherwise.
- **Kits are downloaded again once.** Each kit is downloaded again on the first review after this build, because the cache key changed.
